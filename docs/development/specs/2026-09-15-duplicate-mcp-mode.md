# Duplicate-MCP Mode Design

**Status:** Proposed
**Date:** 2026-09-15
**Branch:** `feature/duplicate-mcp-mode`

---

## Problem

When a user configures `portcullis-gate` as an MCP server in more than one MCP client (e.g. Claude Desktop and Claude Code / Cursor), both clients launch separate `portcullis-gate` processes from the same configuration file. Both processes attempt to bind the management UI port (default `7777`) on startup. The first process to start wins the bind. The second process fails with a fatal error and the MCP client loses its gate connection entirely.

Even if the second process is made to survive the bind failure, a deeper problem remains: the management UI port is also the OIDC redirect URI target. When the user authenticates via a browser-based OIDC login flow, the IdP redirects back to `localhost:7777`. The process that owns port `7777` receives the callback — but this may not be the process the user is actively working with. The PKCE session state (the `state` parameter, `code_verifier`, and `nonce`) was generated by whichever process initiated the login, and lives only in that process's memory. If the callback arrives at a different process, it cannot complete the token exchange.

This is a known defect in the MCP host layer. There is no upstream fix on the horizon. Portcullis needs to work around it.

---

## Constraints

- Both gate instances use the same `gate.yaml` configuration file.
- The user cannot control which instance their MCP client is talking to.
- The instance that owns port `7777` (the "primary") may be idle — receiving no MCP tool calls — while the instance the user is actively using (the "secondary") cannot bind the port.
- No network IPC between the two instances is acceptable (adds complexity, attack surface, and port management overhead).
- Writing an OIDC token to disk is a security trade-off. It is accepted here because the problem cannot be solved otherwise, and the alternative (a non-functional gate) is worse.

---

## Solution Overview

Introduce a `duplicate_mcp_hack: true` configuration flag. When enabled, the two instances coordinate via two files on disk:

| File | Purpose | Lifetime |
|---|---|---|
| `~/.portcullis/oidc-pkce-session.json` | PKCE session written by the secondary before login; read by the primary to complete the callback | Deleted immediately when state is matched in `HandleCallback`, regardless of whether the token exchange succeeds |
| `~/.portcullis/oidc-login.token` | JWT written by `OIDCLoginManager` after a successful token exchange or refresh | Deleted by the primary when the session expires; overwritten on each refresh |

Both files are written with mode `0600`. The parent directory is created with mode `0700` if it does not exist.

## Detailed Flow

### Normal startup

Both instances start and attempt to bind port `7777`.

- The first instance to bind succeeds. It operates normally. This is the **primary**.
- The second instance fails to bind. With `duplicate_mcp_hack: true`, this is non-fatal. It logs a warning, sets `isSecondary = true`, and starts a token file poller. This is the **secondary**.

### Login initiated from the secondary (primary use case)

This is the expected common case — the user is working in the MCP client whose gate instance is the secondary.

```
Secondary                           Primary (idle)             Browser / IdP
---------                           --------------             ---------
StartLogin()
  generate state, code_verifier,
  nonce → store in memory
  write pkce-session.json (0600)
  return auth URL
                                                               user opens auth URL
                                                               user logs in at IdP
                                                               IdP redirects →
                                    HandleCallback(state, code)
                                    state not in own session map →
                                    read pkce-session.json
                                    state matches →
                                    delete pkce-session.json  ← immediately, before exchange
                                    exchange code for tokens
                                    validate nonce
                                    writeTokenFile(jwt)       ← write oidc-login.token (0600)
                                    serve "you may close this window"
[token file poller fires]
SetToken(jwt)
StateMachine → Authenticated
[tool calls proceed normally]
```

### Login initiated from the primary (secondary use case)

Less common — the user happens to trigger a login from the primary's MCP client.

The primary processes the callback entirely from its own in-memory PKCE session (existing behaviour). After a successful exchange, `OIDCLoginManager.writeTokenFile` writes the token file. The secondary's poller picks it up and authenticates.

### Token refresh

When the primary's background refresh loop obtains a new access token, it calls `writeTokenFile` with the new JWT. The secondary's poller detects the content change and calls `SetToken` on its own `IdentityCache`, keeping the secondary's identity current.

### Session expiry

When the primary's refresh token expires naturally (`invalid_grant`) or refresh fails, the primary deletes `oidc-login.token`. The secondary's `TokenFilePoller` detects the file's disappearance on its next tick and invokes the callback with an empty string `""`. The secondary calls `identity.Clear()` and `stateMachine.SetUnauthenticated()`, returning cleanly to the unauthenticated state and prompting the user to log in again.

## File Formats

### `oidc-pkce-session.json`

Written by the secondary's `OIDCLoginManager.StartLogin`. Deleted by the primary's `HandleCallback` the moment a matching `state` is found — before the token exchange is attempted.

```json
{
  "state":          "base64url-random-32-bytes",
  "code_verifier":  "base64url-random-64-bytes",
  "nonce":          "base64url-random-32-bytes",
  "expires_at":     "2026-09-15T14:35:00Z"
}
```

The `expires_at` field matches the in-memory PKCE session expiry (default 10 minutes). The primary rejects sessions that have expired.

### `oidc-login.token`

A raw JWT string (the OIDC ID token), terminated with a newline. This is the same format used by the existing `oidc-file` identity strategy, making the on-disk representation consistent.

## Component Changes

### `Config` (config.go)

New top-level field:

```yaml
duplicate_mcp_hack: true
```

New fields under `identity.config` (for `oidc-login` strategy):

```yaml
identity:
  strategy: oidc-login
  config:
    token_cache_file:  ~/.portcullis/oidc-login.token       # default
    pkce_session_file: ~/.portcullis/oidc-pkce-session.json # default
```

Both fields require `yaml` and `mapstructure` struct tags for correct decoding from the raw config map.

**Validation rules:**
- `duplicate_mcp_hack: true` requires `identity.strategy: oidc-login`.
- `duplicate_mcp_hack: true` is forbidden in multi-tenant mode.

### `OIDCLoginManager` (oidclogin.go)

`OIDCLoginManager` owns the entire on-disk file lifecycle for duplicate-mcp mode. `IdentityCache` remains a pure memory-only cache and never writes to disk under `oidc-login`.

- New fields: `pkceSessionFile string`, `tokenCacheFile string`.
- `StartLogin`: after releasing `m.mu`, write `pkce-session.json` if `pkceSessionFile` is set. Log at `Debug` level: `"duplicate-mcp: wrote PKCE session file"`.
- `HandleCallback`: if `state` is not found in the in-memory session map and `pkceSessionFile` is set, read the file. If the state matches and is not expired, **delete the file immediately** (before attempting the token exchange) and log at `Info` level: `"duplicate-mcp: completing token exchange using PKCE session file"`. Complete the exchange using the file's `codeVerifier` and `nonce`. On success, call `writeTokenFile`.
- `refreshLoop`: call `writeTokenFile` after each successful refresh, logging at `Debug` level: `"duplicate-mcp: token file updated after refresh"`. When the session goes unauthenticated (natural expiry or refresh failure), delete `tokenCacheFile` and log at `Info` level: `"duplicate-mcp: token file deleted; secondary instance will return to unauthenticated state"`.
- `writeTokenFile(idToken string)`: private helper. Expands path, creates parent dirs (`0700`), writes JWT + newline with mode `0600`. Logs warning on failure.

**Mutex discipline:** Never perform disk I/O while holding `m.mu`. Lock only to read or modify in-memory state, then unlock before touching files.

### `IdentityCache` (identity.go)

No change to `SetToken`. It updates the in-memory cache only. It does not write to disk under any strategy. Token file writing is the responsibility of `OIDCLoginManager`.

### `TokenFilePoller` (token_file_poller.go, new)

Polls a file path at a configurable interval (default 5 seconds). Tracks `lastSeen string` and `hadContent bool`.

- If the file is missing or empty and `hadContent` is true: invoke `onToken("")`, reset state.
- If the file has content differing from `lastSeen`: invoke `onToken(jwt)`, update state.
- Stops when its context is cancelled.

### `Gate` (server.go)

- New field: `isSecondary bool` — set to `true` when the gate boots in secondary mode.
- If `cfg.DuplicateMCPHack` is true and `mgmt.Start` returns an error, set `g.isSecondary = true` and emit a `Warn` log explaining that secondary mode is active and that OIDC credentials will be obtained via the token file written by the primary instance.
- If `cfg.DuplicateMCPHack` is false and `mgmt.Start` returns an error, return the fatal error as today, but first emit an `Info` log explaining that on Windows, Claude Desktop launches two copies of each MCP server, and that setting `duplicate_mcp_hack: true` in `gate.yaml` can mitigate this problem.
- If `g.isSecondary`, start a `TokenFilePoller` whose `onToken` callback:
  - `jwt != ""`: call `g.identity.SetToken(jwt)`, on success call `g.stateMachine.SetAuthenticated()`. Log at `Info` level noting the token was picked up from the token file due to duplicate-mcp mode.
  - `jwt == ""`: call `g.identity.Clear()`, call `g.stateMachine.SetUnauthenticated()`. Log at `Warn` level noting the token file has disappeared and the gate has returned to unauthenticated state.

## Known Limitations

**Primary process must stay alive.** If the primary process is killed before the user completes login, nobody is listening on port `7777` and the browser will receive a connection refused error. In practice this should not occur — MCP clients keep launched processes alive for the duration of the session. The primary may be idle (receiving no tool calls) but its goroutines, including the management HTTP server, continue running.

**Concurrent logins.** If both instances independently start a login flow at the same time, the PKCE session file holds only one session. The second write overwrites the first. One of the two login attempts will fail. This is an unlikely edge case — it requires both instances to prompt for login at exactly the same moment — and is not addressed in this design.

**Single-user, single-machine assumption.** The file-based coordination assumes both gate instances run as the same OS user on the same machine. This is always true for stdio-based MCP clients but would not hold for any hypothetical remote or multi-user deployment.

---

## Security Considerations

Writing OIDC tokens to disk is a recognised security trade-off:

- Any process running as the same OS user can read `~/.portcullis/oidc-login.token` and obtain a valid bearer token.
- The PKCE session file is lower risk (it is only useful during the narrow login window and is deleted immediately after state is matched) but is also written `0600`.
- Users who are not affected by the double-launch problem should leave `duplicate_mcp_hack: false`. No files are written in that case.
- This mode should be clearly labelled in documentation as a workaround for a host-layer defect, not a general-purpose feature.

The threat model for this mode is: the gate is running on a developer workstation where the user is the sole account holder. Enterprise deployments or shared systems should not use this flag.
